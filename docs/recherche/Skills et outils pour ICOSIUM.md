# Brancher chaque outil là où Claude regarde

**Le point essentiel : ICOSIUM avance dans des fils (threads) d'un projet claude.ai, et ces fils lisent le `CLAUDE.md` du dépôt mais ignorent les compétences (skills), les serveurs MCP et les réglages qu'on range dans le dépôt** ([Projects docs](https://code.claude.com/docs/en/claude-projects.md)). Installer un outil « dans le dépôt » ne suffit donc pas : chaque outil doit aller à l'un des trois bons endroits. Le premier, ce sont les **réglages du compte et du projet claude.ai** (compétences, plugins, connecteurs). Le deuxième, c'est le **script d'installation de l'environnement cloud** (paquets, navigateur pour les captures, accès réseau). Le troisième, c'est le **dépôt lui-même**, pour la qualité vérifiable : intégration continue (CI), tests, captures d'écran à 360 px. Côté compétences, il suffit au départ de cinq paquets officiels : Supabase (sécurité RLS), Vercel (règles d'interface et de performance React), Anthropic `frontend-design` et `skill-creator`, et les tests navigateur Playwright. Il faut y ajouter deux connecteurs de documentation gratuits, Context7 et LiveKit Docs. Le vrai filet de sécurité n'est pourtant pas une compétence : c'est une **CI GitHub obligatoire avant chaque fusion** et une **galerie de captures 360 px clair/sombre** que le propriétaire peut regarder sans lire de code. Les compétences publiées par des inconnus présentent un vrai risque d'attaque. ICOSIUM ne doit installer que des paquets d'éditeurs officiels, relus avant activation.

## Trois endroits d'installation, dont un seul que les fils de projet lisent vraiment

La documentation officielle est explicite : « Cloud threads load each repository's CLAUDE.md instructions but not its skills, `.mcp.json` servers, or `.claude/settings.json` » ([Projects docs](https://code.claude.com/docs/en/claude-projects.md)). Concrètement, un fil de projet ICOSIUM lit le `CLAUDE.md` à la racine, `.claude/CLAUDE.md` et `.claude/rules/`. Il ne charge **ni les `CLAUDE.md` des sous-dossiers, ni les règles limitées à un chemin, ni `.claude/skills/`, ni `.mcp.json`, ni les hooks, ni les règles de permission, ni les variables `env`** ([Projects docs](https://code.claude.com/docs/en/claude-projects.md)). La commande `/plugin` n'existe pas non plus dans les sessions cloud ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web.md)). Toute consigne vitale pour ICOSIUM doit donc vivre dans le `CLAUDE.md` racine. Un futur `apps/web/CLAUDE.md` serait invisible.

Chaque type d'outil a donc son bon chemin. Les compétences s'activent **sur le compte claude.ai** et se synchronisent au démarrage de chaque fil ([Skills](https://code.claude.com/docs/en/skills.md)). Les plugins s'ajoutent dans **Project settings > Plugins**. Les serveurs MCP deviennent des **connecteurs** sur claude.ai/customize/connectors. Les outils en ligne de commande s'installent dans le **script d'installation de l'environnement** ([Projects docs](https://code.claude.com/docs/en/claude-projects.md)). Les instructions de projet (jusqu'à 16 000 caractères) et la mémoire de projet sont envoyées à chaque nouveau fil. Ce sont des consignes que Claude suit, pas des règles imposées ([Projects docs](https://code.claude.com/docs/en/claude-projects.md)).

| Ce qu'on veut | Mis dans le dépôt | Ce qui marche dans un fil de projet ICOSIUM |
| --- | --- | --- |
| Consignes du projet | `CLAUDE.md` racine | Chargé |
| Compétences | `.claude/skills/` | Ignoré : activer sur le compte claude.ai |
| Serveurs MCP | `.mcp.json` | Ignoré : connecteurs claude.ai |
| Plugins | `.claude/settings.json` | Ignoré : Project settings > Plugins |
| Hooks, permissions, `env` | `.claude/settings.json` | Ignoré : CI + instructions de projet + variables de l'environnement cloud |
| Paquets, navigateur | (rien) | Script d'installation de l'environnement |

Ranger quand même les compétences et un `.mcp.json` dans le dépôt garde un intérêt réel, mais secondaire. Cela donne une copie versionnée et relisible en pull request, utile pour une session sur ordinateur ou une session cloud hors projet ([Cloud environments](https://code.claude.com/docs/en/cloud-environments.md)). Ce n'est pas le filet de sécurité.

## Cinq paquets officiels couvrent les besoins, les compétences 3D attendront

**Supabase est la priorité absolue**, parce que la règle n° 2 d'ICOSIUM (aucune main ni pioche lisible par un autre joueur) repose sur la RLS. Le dépôt `supabase/agent-skills` (licence MIT) fournit deux compétences. `supabase` couvre Auth, Realtime, les migrations, `@supabase/ssr` dans Next.js et les audits de sécurité. `supabase-postgres-best-practices` contient une catégorie « Security & RLS (Critical) » ([README](https://raw.githubusercontent.com/supabase/agent-skills/main/README.md)). Le serveur MCP Supabase déjà branché recommande lui-même `npx skills add supabase/agent-skills` ([Supabase AI skills](https://supabase.com/docs/guides/getting-started/ai-skills.md)). Ces compétences rappellent les pièges que la recherche a relevés. Une fonction `security definer` doit fixer `search_path`. Par défaut, toute fonction est appelable en RPC même par `anon` tant qu'on ne révoque pas `execute` ([Supabase Database Functions](https://supabase.com/docs/guides/database/functions.md)). Les mains doivent passer par des canaux Realtime **privés**, avec « Allow public access » désactivé ([Supabase Realtime Authorization](https://supabase.com/docs/guides/realtime/authorization.md)).

**Vercel apporte les règles d'interface.** `vercel-labs/agent-skills` contient `web-design-guidelines` : plus de 100 règles sur l'accessibilité, le focus, les zones tactiles, `prefers-reduced-motion`, l'i18n via `Intl` et le mode sombre. Il contient aussi `react-best-practices` (40+ règles de performance) et `react-view-transitions` ([README](https://raw.githubusercontent.com/vercel-labs/agent-skills/main/README.md)). Une réserve s'applique à cette dernière : les View Transitions de Next.js 16 sont encore marquées « not recommended for production » ([Next.js docs](https://nextjs.org/docs/app/api-reference/config/next-config-js/viewTransition)). Elle passe donc en second rang. Aucun fichier de licence n'a été trouvé à la racine de ce dépôt, un point à vérifier avant de copier ses compétences.

**Anthropic couvre le design et l'outillage.** Le plugin `frontend-design` du répertoire officiel `claude-plugins-official` (licence Apache) oblige Claude à choisir une direction esthétique, à éviter les choix par défaut, à poser un petit système de tokens et à garder un plancher qualité : mobile, focus clavier, mouvement réduit ([marketplace.json](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/.claude-plugin/marketplace.json) ; [ClaudeLog](https://claudelog.com/faqs/what-is-frontend-design-skill-in-claude-code/)). C'est exactement la demande du propriétaire, « jamais générique ni template ». Le même répertoire propose `skill-creator`, `security-guidance` (alertes sur l'injection, le XSS et les secrets en dur), ainsi que `playwright` et `context7` ([marketplace.json](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/.claude-plugin/marketplace.json)). `skill-creator` sert à écrire les compétences propres à ICOSIUM : le contrat des jeux (`minPlayers`, `options`, vue filtrée, `botAllowed`), la procédure « i18n + CSS logique » et la procédure « vérifier les écrans à 360 px ». Les règles d'écriture officielles demandent un corps de moins de 500 lignes, une description à la troisième personne et au moins trois évaluations ([Skill authoring best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices)).

**Next.js n'a presque plus besoin de compétence.** ICOSIUM utilise Next 16.4.5 (d'après `pnpm-lock.yaml`). Depuis la version 16.3, la documentation est livrée dans `node_modules/next/dist/docs/`, et `next dev` génère un `AGENTS.md`/`CLAUDE.md`. Les anciennes compétences `next-best-practices` ont disparu au profit de ce mécanisme ([vercel-labs/next-skills](https://raw.githubusercontent.com/vercel-labs/next-skills/main/README.md)). Il faut seulement vérifier où ce fichier généré atterrit, pour qu'il n'écrase pas le `CLAUDE.md` racine. Ce point n'a pas été vérifié.

Deux paquets sont écartés exprès. Les compétences officielles de LiveKit visent les **agents vocaux IA** (Agents SDK), pas les salons audio entre humains d'ICOSIUM ([livekit/agent-skills](https://raw.githubusercontent.com/livekit/agent-skills/main/README.md)). Seul leur serveur de documentation est utile. Pour three.js et React Three Fiber, **aucune compétence officielle n'existe**. `emalorenzo/three-agent-skills` (`r3f-best-practices`, 70+ règles) et d'autres circulent via des annuaires communautaires ([Vibe Index](https://www.vibeindex.ai/skills/emalorenzo/three-agent-skills/r3f-best-practices)). Mieux vaut écrire une petite compétence maison avec `skill-creator`, à partir du guide officiel R3F. Ce guide recommande `frameloop="demand"` avec `invalidate()`, `instancedMesh` pour les 28 dominos, et `PerformanceMonitor` pour baisser la qualité sur les téléphones faibles ([R3F Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)).

Côté connecteurs, Supabase, Vercel et GitHub sont déjà branchés. Il faut en ajouter deux, sans installation locale. **Context7** fournit une documentation à jour des bibliothèques via `https://mcp.context7.com/mcp` ([plugin .mcp.json](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/external_plugins/context7/.mcp.json)). **LiveKit Docs**, gratuit, est accessible via `https://docs.livekit.io/mcp` ([LiveKit MCP](https://docs.livekit.io/intro/mcp-server/)). Les serveurs Playwright MCP, Chrome DevTools MCP et `next-devtools-mcp` ont besoin d'un navigateur ou d'un `next dev` qui tourne sur place ([next-devtools-mcp](https://raw.githubusercontent.com/vercel/next-devtools-mcp/main/README.md)). Le dépôt Playwright conseille d'ailleurs aux agents de code sa CLI et ses compétences plutôt que le MCP, parce qu'elles consomment moins de contexte ([Playwright MCP](https://raw.githubusercontent.com/microsoft/playwright-mcp/main/README.md)). Pour ICOSIUM, `@playwright/test` installé dans le dépôt et lancé par Claude dans le conteneur suffit.

## La qualité se prouve par une CI et des captures, pas par des consignes plus fortes

La documentation d'Anthropic sépare deux familles d'outils. Le `CLAUDE.md` et les compétences sont suivis « nearly every time », sans garantie. Les hooks, la CI et la protection de branche, eux, sont imposés, et c'est « a person who approves the merge » qui a le dernier mot ([Best practices](https://code.claude.com/docs/en/best-practices)). Comme les fils de projet ignorent les hooks, **la CI GitHub est la seule barrière automatique qui s'applique à ICOSIUM.** Aujourd'hui, le dépôt n'a ni dossier `.github/`, ni ESLint, ni Playwright, ni script de lint. Trois étapes comblent ce manque.

La première étape est un **lint**. Next.js 16 a supprimé `next lint`. Il faut passer par la CLI ESLint avec un `eslint.config.mjs` qui combine `eslint-config-next/core-web-vitals`, `eslint-config-next/typescript` et `eslint-config-prettier/flat`, plus `settings.next.rootDir: 'apps/web/'` pour le monorepo ([Next.js ESLint](https://nextjs.org/docs/app/api-reference/config/eslint)). Une règle doit interdire `ml-`, `mr-`, `left-` et `right-`, au service de la règle n° 6 (droite à gauche). Attention : ESLint 10 exige Node `^20.19`, `^22.13` ou `>=24`, alors que le `package.json` d'ICOSIUM annonce `>=20.9` ([Next.js ESLint](https://nextjs.org/docs/app/api-reference/config/eslint)). Il faut monter ce plancher.

La deuxième étape est **un seul script `pnpm verify`** qui enchaîne typecheck, lint, Vitest et build, avec un workflow `.github/workflows/ci.yml` qui le lance sur chaque pull request. Le propriétaire le déclare ensuite « required check » dans la protection de la branche `main`. Le détecteur de secrets `gitleaks/gitleaks-action` s'y ajoute, gratuit pour un compte personnel ([gitleaks-action](https://github.com/gitleaks/gitleaks-action)). Les tests pgTAP de la RLS (`supabase test db`) demandent Docker, que le propriétaire n'a pas, mais que les machines GitHub Actions ont déjà. La documentation Supabase fournit le workflow `db-tests.yml` correspondant ([Supabase Testing](https://supabase.com/docs/guides/local-development/testing/overview.md)), et `supabase-test-helpers` sert à simuler plusieurs joueurs ([basejump](https://github.com/usebasejump/supabase-test-helpers)). Ces tests prouvent automatiquement que le joueur B ne voit jamais la main du joueur A.

La troisième étape, c'est **ce que le propriétaire regarde**. Playwright `toHaveScreenshot()` compare chaque écran à une image de référence enregistrée. Ces références dépendent du système d'exploitation, il faut donc les générer et les comparer au même endroit ([Playwright snapshots](https://playwright.dev/docs/test-snapshots)). Deux projets Playwright suffisent, à 360 × 780 px, en `colorScheme` clair et sombre, avec `reducedMotion: 'reduce'` pour figer les animations. La CI publie le rapport avec les images, que le propriétaire ouvre comme une galerie. Chaque pull request reçoit aussi un lien de prévisualisation Vercel à ouvrir sur son téléphone. La fonction « Protection Bypass for Automation », disponible sur tous les plans Vercel, permet à Playwright de tester ces prévisualisations protégées ([Vercel docs](https://vercel.com/docs/deployment-protection/methods-to-bypass-deployment-protection/protection-bypass-automation)). Après chaque migration, l'outil `get_advisors` du connecteur Supabase sort les alertes de sécurité. Claude doit en coller le résultat dans la pull request.

Le `CLAUDE.md` (123 lignes) reste sous la limite conseillée d'environ 200 lignes. Il lui manque pourtant l'élément le plus utile selon Anthropic : **les commandes exactes de vérification**, y compris comment lancer un seul fichier de test ([Best practices](https://code.claude.com/docs/en/best-practices)). Une bonne partie de sa prose sur l'ambiance existe déjà dans `docs/ICOSIUM.md` et peut être raccourcie. Les **instructions de projet** sur claude.ai doivent reprendre les formules officielles. Avant de dire que c'est fini, Claude lance la vérification et colle le résultat. S'il manque quelque chose, il le dit et s'arrête, sans simuler ni deviner. Il ne fusionne pas et ne touche pas à la CI sans l'accord du propriétaire ([Projects docs](https://code.claude.com/docs/en/claude-projects.md)). L'action `anthropics/claude-code-action@v1` peut ajouter une relecture automatique de chaque pull request avec un `CLAUDE_CODE_OAUTH_TOKEN` d'abonnement Pro ou Max ([claude-code-action](https://github.com/anthropics/claude-code-action) ; [setup.md](https://github.com/anthropics/claude-code-action/blob/main/docs/setup.md)). Elle consomme du quota à chaque envoi. L'« Auto-fix » des sessions cloud, qui corrige seul les échecs de CI ([Claude Code on the web](https://code.claude.com/docs/en/claude-code-on-the-web)), donne une bonne partie de ce bénéfice sans coût de CI. Il vaut mieux commencer par lui.

## Le script d'installation porte les paquets, le réseau et les secrets

Le script d'installation est un script Bash qui tourne en root sur Ubuntu 24.04 **avant** le démarrage de Claude. S'il finit en moins d'environ cinq minutes, le disque est photographié et réutilisé pendant environ sept jours ([Cloud environments](https://code.claude.com/docs/en/cloud-environments.md)). Node 22, pnpm, eslint, prettier, PostgreSQL 16, gh et jq sont déjà installés ([Cloud environments](https://code.claude.com/docs/en/cloud-environments.md)). Voici une version de départ, qui reste à valider dans un fil, car le dossier où le script s'exécute n'est pas documenté :

```bash
#!/bin/bash
set -e
cd "$(git rev-parse --show-toplevel 2>/dev/null || echo /home/user/icosium)"
corepack enable                      # uses pnpm@10.28.0 from package.json
pnpm install --frozen-lockfile &
# once @playwright/test is in apps/web:
# pnpm --filter @icosium/web exec playwright install --with-deps chromium &
wait
```

Si le dépôt n'est pas encore cloné quand le script tourne, les instructions de projet doivent demander à Claude de lancer `pnpm install` en début de fil.

**Le réseau par défaut (« Trusted ») autorise npm et GitHub, mais pas `supabase.co` ni `vercel.com`** ([Cloud environments](https://code.claude.com/docs/en/cloud-environments.md)). Il faut passer en accès **Custom** en cochant « Also include default list of common package managers », puis ajouter `*.supabase.co`, `vercel.com`, `*.vercel.app` et `*.livekit.cloud`. Il faudra aussi ajouter les hôtes de téléchargement des navigateurs Playwright, que la recherche n'a pas pu confirmer : le journal d'erreur de la première installation les donnera. **Aucune clé secrète ne va dans les variables d'environnement**, que tout utilisateur de l'environnement peut lire. Il faut utiliser les « network secrets », que le proxy attache à un hôte précis sans que la session les voie jamais ([Cloud environments](https://code.claude.com/docs/en/cloud-environments.md)). Reste à tester que ce mécanisme s'accorde avec l'en-tête `apikey` du client Supabase.

## Les compétences tierces sont la porte d'entrée préférée des attaquants

Un audit de Snyk publié en février 2026, cité ici d'après un résumé de seconde main, aurait analysé 3 984 compétences sur ClawHub et skills.sh. Il y aurait trouvé **13,4 % de problèmes critiques, 36 % de compétences contenant une injection de consignes et 1 467 charges malveillantes**. On y voit des instructions cachées (Unicode invisible, Base64, « ignore previous instructions »), des commandes qui téléchargent puis exécutent un script, ou des vols de clés SSH et AWS ([DEV Community](https://dev.to/ventureio/are-claude-skills-safe-in-2026-what-the-snyk-toxicskills-audit-actually-found-1315), citant [Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/)). L'auteur du résumé vend lui-même des compétences, et ses chiffres n'ont pas été recoupés avec le rapport original. Le risque, lui, est confirmé par Anthropic : son répertoire officiel prévient qu'il « does not control what MCP servers, files, or other software are included in plugins » ([claude-plugins-official README](https://raw.githubusercontent.com/anthropics/claude-plugins-official/main/README.md)). Autre signal d'alarme : un annuaire tiers affiche, sous le nom `vercel-labs/agent-skills`, des entrées suspectes nommées `hacked_skill` ou `subpath-escape` ([Vibe Index](https://vibeindex.ai/collection/vercel-labs/agent-skills)). **On n'installe jamais depuis un annuaire, seulement depuis le dépôt GitHub officiel de l'éditeur.**

Pour un propriétaire qui ne lit pas le code, la règle pratique tient en une phrase : **chaque compétence arrive dans sa propre petite pull request, copiée en clair (`--copy`, pas de lien symbolique), à une version fixée, et Claude rend compte de sa relecture avant que le propriétaire l'active sur son compte.** Cette relecture consiste à passer `cat -v` sur chaque `SKILL.md` pour repérer les caractères invisibles, à lister chaque script et chaque commande réseau, à vérifier que les outils demandés (`Bash`, `WebFetch`) correspondent au besoin, et à confirmer la licence ([DEV Community](https://dev.to/ventureio/are-claude-skills-safe-in-2026-what-the-snyk-toxicskills-audit-actually-found-1315)). La CLI `npx skills` accepte une version fixée (`owner/repo@v1.2.3`) et envoie une télémétrie anonyme, qu'on coupe avec `DISABLE_TELEMETRY=1` ([vercel-labs/skills](https://raw.githubusercontent.com/vercel-labs/skills/main/README.md)). Dans un `.mcp.json`, on fixe aussi les versions (`next-devtools-mcp@0.4.0`, `@playwright/mcp@0.0.84`) au lieu de `@latest`. Les compétences qui embarquent des scripts, comme `webapp-testing` ou `skill-creator`, exécutent du code dans le conteneur : c'est acceptable venant d'Anthropic, mais seulement après relecture.

L'ordre ci-dessous suit la valeur pour ICOSIUM. Les bibliothèques de la dernière table sont des **dépendances importantes** : selon le `CLAUDE.md`, chacune doit être proposée au propriétaire, avec une ou deux phrases d'explication, avant d'être ajoutée.

## Conclusion

Le travail le plus rentable ici n'est pas d'empiler des compétences, mais de **déplacer les garanties de la parole vers la machine**. Dans un fil de projet, tout ce qui n'est ni dans le `CLAUDE.md` racine, ni dans un réglage claude.ai, ni vérifié par la CI relève de la bonne volonté. Pour un propriétaire qui ne lit pas le code, la preuve visible prime donc sur l'outil : un test pgTAP qui échoue si une main fuit, une capture 360 px qui change, un lien de prévisualisation à ouvrir sur son téléphone. Les compétences restent utiles comme aides, mais les meilleures pour ICOSIUM n'existent pas encore. Ce seront les compétences maison, écrites avec `skill-creator`, qui figeront le contrat des jeux, les canaux Realtime privés et le style « café algérien de nuit ».

Plusieurs points restent à vérifier en conditions réelles avant d'en faire des certitudes. Il faut savoir si le plugin Supabase est proposé dans Project settings > Plugins ou s'il faut envoyer un zip, dans quel dossier tourne le script d'installation, quels hôtes Playwright ouvrir, si les network secrets s'accordent avec l'en-tête `apikey` de Supabase, et où `next dev` écrit son `CLAUDE.md`. La première étape d'outillage devrait servir à trancher ces cinq questions dans un vrai fil, avant toute autre installation.
